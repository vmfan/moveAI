# Implementation Roadmap — Intake → Quote → Booking Workflow

Tracks the sequential builds that wrap the existing single-image volume-estimation pipeline (`moveai_prototype/`) in the full customer workflow specified in `DESIGN.md`. Each build gets its own plan-mode session: read this file, confirm scope for that build only, execute, verify, update status here, stop. Don't start a build whose dependencies aren't marked complete. Each build's session ends with a commit containing both the code changes and this file's updated status/notes — the status table is only trustworthy if it stays synchronized with git history, so a build isn't real until it's committed.

Builds 1-7 delivered the Streamlit MVP. Builds 8-14 begin a second phase: rebuilding the UI layer as a **FastAPI backend + Next.js/React + Tailwind frontend**, with true server-enforced linear gating (today's Streamlit sidebar lets a customer jump to any page; it only redirects with a friendly link rather than truly blocking) and a more production-grade look for grading. All Build 1-7 business logic (`db.py`, `pricing.py`, `boxed_goods.py`, `priors.py`, `review_policy.py`, `inventory_sync.py`, `quote_sync.py`, `booking_sync.py`) is reused unchanged — confirmed Streamlit-free during planning — as is the AI pipeline (`pipeline.py`, `geometry.py`, `visualization.py`); only `job_context.py`'s session/query-param glue is replaced with a URL-path-param scheme, and `models.py` gains a caching wrapper so models aren't reloaded from disk on every call.

## How to resume

1. Read `DESIGN.md` first — the product vision and the contracts (especially §5a inter-stage schemas and §5c volume→quote contract) that every build must satisfy.

## Build notes

**Build 1 — axis-semantics fix.** `ObjectMeasurement.dimensions_m` (`geometry.py`) discarded which fitted-box extent was width/height/depth. Fixed by classifying each local box axis via the box's rotation `box.R` against camera-frame axes (depth ≈ camera-forward, height ≈ up, remainder is width), replacing `dimensions_m: np.ndarray` with named `width_m`/`height_m`/`depth_m` fields and adding `used_axis_aligned_fallback: bool`. Call sites updated: `app.py` (two unpacking sites + UI column labels), `smoke_test.py` (JSON export field names), and `generate_presentation_assets.py` (missed by the original plan — found by grep, consumed `smoke_test.py`'s old `obb_edges_m` JSON key in two places).

Verification note: the full pipeline couldn't run end-to-end in this environment (Grounding DINO isn't cached locally and `local_files_only=True` blocks the download — pre-existing, unrelated to this change). Verified instead with a synthetic-scene unit check that exercises the real `measure_detection`/`_named_dimensions` code path via Open3D: a frontal-shell object correctly resolves `depth_m` as the smallest axis, plus direct checks of `_named_dimensions` against identity and rotated rotation matrices. All four edited files pass `py_compile`.

**Build 2 — SQLite persistence layer.** New `db.py`: tables for `job`, `intake`, `inventory_item` (unifies measured/prior_assisted/declared items and boxed-goods lines via `measurement_basis` + `is_boxed_goods`), `pricing_config` (company-configurable, seeded with a default row, currency HKD), `quote`/`quote_line` (versioned — new quotes are inserted, never mutated, prior version flagged superseded), `booking`. See `DESIGN.md` §5a/§5c for the contracts this schema must satisfy. Stdlib `sqlite3` only, no ORM; module stays free of Streamlit/pipeline imports so it can run without the model stack. `config.py` gained `DB_PATH` (overridable via `MOVEAI_DB_PATH`).

Contracts from §5a/§5c are enforced as schema `CHECK` constraints rather than left as convention: boxed-goods lines can't carry dimensions, `measured` items can't carry `prior_assisted_axes`, `quote_line.surcharge_eligible` is forced to agree with `measurement_basis` (the surcharge contract), and a partial unique index caps `pricing_config` at one active row. `customer_confirmed` is a column separate from `review_state` so confirming an item structurally cannot clear a staff escalation. Quotes are versioned by inserting a new row and flagging the previous one superseded within `create_quote()`, never mutating in place.

**Build 3 — pricing engine + boxed-goods estimator.** Pure functions, no I/O, mirroring `pipeline.py`/`geometry.py` in staying Streamlit-agnostic. `upper_bound_volume_m3()` is the single place the margin is applied — `pricing_smoke_test.py` proves this by asserting `Σ line.volume_m3 == upper_bound_volume_m3(Σ line_raw, margin)` to float tolerance, which only holds if margin was applied exactly once. `access_multiplier()` combines origin/destination legs from intake floor/lift/parking data **additively** (each leg's surcharge is summed, not compounded) — see the market research below for why. Boxed-goods gets its own labour weight (`boxed_goods_labour_multiplier`) applied only to `is_boxed_goods` lines. `recommend_truck()` is a separate function from pricing per `DESIGN.md` §5c, selecting the smallest truck whose *usable* capacity (72% of nominal, honestly stated as a fitting-geometry factor, not a second margin) clears both volume and the largest item dimension; escalates `oversize_item` when nothing fits and computes multi-trip counts when volume exceeds the whole fleet.

`priors.py` is the single class-priors artifact `DESIGN.md` §4 calls for, serving one of its three jobs this milestone: `boxes_for_storage_label()` is populated with box-count ratios, consumed by `boxed_goods.py`'s `estimate_boxed_goods()`. The other two jobs — `flag_implausible_dimension()` (plausibility bounds) and `expected_depth_m()` (occluded-axis substitution) — are explicit stubs returning no signal, per the roadmap's original scope. `DimensionFlag` carries a `has_prior: bool` alongside `flagged` so a caller (Build 5) can tell "no prior exists" apart from "checked and plausible" rather than reading a bare `False` as an endorsement — this wasn't in the original build note but followed directly from keeping the stub honest.

Also added beyond the original build note, both scoped in during planning once market research was available: **`declared_excess_surcharge()`** in `pricing.py` implements `DESIGN.md` §5c's day-of surcharge contract (fires only on `declared`-quantity error, never on `measured`/`prior_assisted` volume) as a tiered function against total price; no new `pricing_config` schema needed. **Recalibration of `db.py`'s seeded `pricing_config`**: `floor_multiplier_per_level` changed `0.08 → 0.15`; `base_callout_fee`/`price_per_m3` left unchanged after cross-checking they land the Consumer Council's worked case in-band.

*Hong Kong market research (via web search, informing the above):* the [HK Consumer Council's 2024 survey of 20 removal companies](https://www.consumer.org.hk/tc/article/573-home-removal-service/573-home-removal-service-price-comparison) found stair/no-lift charges (樓梯費) run **15–20% of the total per floor** (a floor = 15–20 steps), up to 30% at the priciest outlier — this set both the recalibrated `floor_multiplier_per_level` and the additive-not-multiplicative leg-combination rule, matching §5c's "never stack" principle. The same survey documents the day-of excess convention: **+20% of total if actual goods exceed the estimate by >20%, +30–50% if by >50%**, which became `DECLARED_EXCESS_TIERS`. No surveyed HK company itemises a parking-distance surcharge (that's a US "long carry beyond 75–100 ft" convention), so `pricing.FREE_CARRY_DISTANCE_M = 20.0` keeps short walks from inflating the quote via the otherwise-unused intake field. Fleet specs (Lalamove/GoGoX public pricing pages, cross-checked against a general HK truck reference table) set `HK_FLEET`: van ~5.7 m³, 14ft/3-tonne ~11 m³, 16ft/5.5-tonne ~18 m³, 9–10-tonne ~33 m³. The Consumer Council's worked standard case (5-person family, North Point→Mei Foo, 40 furniture items + 35 cartons, quoted HK$3,818–12,162, 2026 mid-size average HK$8,000–12,000) is used twice as a calibration anchor: `pricing_smoke_test.py` reconstructs it and asserts the resulting price lands in that band (got ~HK$10,600 for a 3rd-floor no-lift origin), and `boxed_goods.estimate_boxed_goods()` reconstructs its storage/room composition and asserts 36 boxes against the surveyed 35.

Covers the no-stacked-margin invariant, access-multiplier arithmetic against the worked HK cases (including the additive-vs-multiplicative distinction and the parking free-threshold), boxed-goods labour isolation, escalated/unmeasured items surfacing on the `Quote` rather than vanishing (§5b), truck selection at capacity boundaries and oversize/multi-trip escalation, all three day-of-surcharge tiers, both boxed-goods calibration cases, the `priors.py` stub's `has_prior` signal, and an integration check piping `build_quote()` output through `db.create_quote()` against a throwaway SQLite file to prove the `CHECK` constraints (not just the dict shape) are satisfied. `db_smoke_test.py` re-run clean (24/24) after the seed recalibration. **Build 5 — Inventory Review page.** Implements the `DESIGN.md` §5b interrupt rule. New `review_policy.py` (pure, no db/Streamlit imports, mirroring `pricing.py`/`priors.py`) turns Build 4's recorded signals into the three named states, resolving a genuine tension in §5b: its interrupt-rule sentence names only shell ratio/border truncation/implausible dimension as customer-confirm triggers ("the customer cannot assess whether a measurement is geometrically sound"), while this roadmap's original Build 5 line separately listed low point count and axis-aligned fallback as signals to act on. Resolved by routing the geometric-soundness signals — ones a customer has no basis to judge — to `staff_escalate` instead of a customer prompt, and reserving `customer_confirm` for signals a plain-language question can resolve. `DESIGN.md` §5b gained a paragraph recording this so the two sections don't read as contradictory to a future reader. Full mapping: border truncation and detection confidence < 0.35 → `customer_confirm`; axis-aligned fallback and point count < 200 → `staff_escalate`; a measurement failure (Build 4, unchanged) → `staff_escalate`; shell ratio/implausible dimension → `customer_confirm`, wired but never fires today since `priors.py`'s two stubs still report `has_prior=False`. Both numeric thresholds are explicit uncalibrated placeholders per `DESIGN.md`'s Calibration section. Precedence is `staff_escalate` > `customer_confirm` > `auto_accept` (an item flagged both ways escalates). `persist_capture()` (`inventory_sync.py`) now calls `classify()` and writes the resulting state instead of relying on the schema's `auto_accept` default.

`inventory_sync.py` also gained the mutation half of the review loop: `seed_boxed_goods()` (idempotent — one boxed-goods line per job, calls the existing `boxed_goods.estimate_boxed_goods()` and seeds it as `customer_confirm` rather than `auto_accept`, since §5c's surcharge contract only stands up if the customer actually saw and owned the count before it entered the quote), `set_boxed_goods_count()`, `confirm_item()`, `apply_customer_correction()`, and `add_declared_item()`.

Two scope calls made explicit during planning, both confirmed with the user rather than assumed: (1) a customer **correction** (not mere confirmation) flips `measurement_basis` from `measured` to `declared` — the number moving forward is what the customer typed, so §5c's day-of surcharge, not the estimation-error margin, covers it if wrong. This reads against §5a's literal "`declared` — no underlying detection at all", so the original measured values are preserved under `provenance_json.customer_override` rather than discarded (§5a: provenance is mandatory), and the page states the surcharge consequence before the customer edits. (2) The page supports **manual add** of a `declared` item the pipeline never saw at all (§5a names this explicitly) — auto-accepted and pre-confirmed, since the customer just typed it in themselves. In both new-item paths and in every state transition, confirming or correcting a `customer_confirm` item promotes it to `auto_accept`, but nothing ever clears a `staff_escalate` state beyond setting `customer_confirmed` — §5b's independence rule, already enforced structurally by `db.py`'s separate columns (Build 2), is now also honoured by every write path that reaches them.

**Build 6 — Quote page.** `pages/3_Quote.py` loads confirmed inventory + intake access factors + active `pricing_config`, calls `pricing.build_quote()` (Build 3, unchanged), and displays the headline price, volume (raw + upper-bound with the margin called out as the one place conservatism is added, per `DESIGN.md` §5c), access multiplier with a plain-language origin/destination breakdown, recommended truck, line items labelled by `measurement_basis` with a "who covers an error" note, escalated/unmeasured items surfaced rather than dropped, a day-of-surcharge explainer against `pricing.DECLARED_EXCESS_TIERS`, and version history. New `quote_sync.py` (pure, no db/Streamlit imports, mirroring `inventory_sync.py`/`pricing.py`) holds the logic the page calls.

Two scope calls made explicit during planning, both confirmed with the user:

(1) **Versioning is staleness-gated, not per-page-load.** The roadmap's original line ("persists as a new quote version on each generation") read literally would insert a version on every Streamlit rerun, since the page recomputes on every widget interaction — that would make the version history meaningless within a single session. `quote_sync.quote_matches()` compares a freshly computed `Quote` against the stored active one (totals, margin, access multiplier, recommended truck, and the line set); the page auto-persists v1 on first visit with no quote, then only offers an explicit **Regenerate quote** button — which inserts the next version — when the comparison says the inventory changed since the active quote. This is the same guard-the-write discipline Build 4 applied inside `app.py`'s `analyze` block, applied here to quote generation instead of capture persistence.

(2) **An unconfirmed customer-confirm flag costs a staff review, not money.** Considered and rejected: flipping an unconfirmed flagged item's `measurement_basis` to `declared` the moment a customer clicks past the warning, which is the only way `db.py`'s `quote_line` CHECK will ever set `surcharge_eligible = 1`. Rejected because `DESIGN.md` §5c's upper-bound margin already prices exactly this risk — a `measured`/`prior_assisted` item being wrong is *"the system's estimation error, and the company absorbs it — that's what the upper-bound margin is for"* — so also surcharging it stacks margin on margin, which §5c bans outright elsewhere. The surcharge is scoped to a customer misstating a quantity they themselves supplied (boxed goods, manual adds, corrections — all `declared` today already); skipping a review prompt on our own measurement is inattention, not that kind of dishonesty, and a liability checkbox at the exact moment of pricing risked being a conversion-killer for no defensible reason. Landed instead: `quote_sync.staff_review_reasons()` names every reason a job can't be auto-approved — unconfirmed `customer_confirm` items, `quote.escalated_item_ids`, `quote.unmeasured_item_ids`, an oversize/multi-trip truck — surfaced as a prominent, non-blocking warning that links back to Inventory Review and states the job will get a staff look before booking. `staff_review_reasons()` is written to be reused as-is by Build 7's booking gate and Company Console.

A third, smaller scope call: the Quote page calls the same idempotent `inventory_sync.seed_boxed_goods()` Build 5's review page calls, rather than assuming the customer already visited Inventory Review — skipping it would silently under-quote by roughly half the household's volume (`DESIGN.md` §3). The seeded line lands `customer_confirm` as designed, which correctly trips the reason-list warning above.

**Build 7 — Booking Confirmation + Company Console.** `db.py`'s `booking` table, `create_booking()`, `update_booking_status()`, and `list_bookings()` existed since Build 2 but were unreachable from the UI, and `JOB_STATUSES`'s `"booked"` value was never set anywhere. This build wires both: `pages/4_Booking.py` (customer) and `pages/5_Company_Console.py` (staff), plus new `booking_sync.py` (pure, no db/Streamlit imports, mirroring `quote_sync.py`) holding the logic both pages call. `db.py` gained three additive helpers with no schema change (`initialize()` uses `CREATE TABLE IF NOT EXISTS`, so a CHECK edit wouldn't apply to existing `job.db` files anyway, and Build 2's schema already covered everything needed): `get_booking()` (no by-id read existed), `list_bookings(..., job_id=...)` (a job filter, plus tie-breaking same-second `created_at` rows by `booking.id DESC` since `_now()` is whole-second ISO), and `update_booking_status(..., customer_note=...)` mirroring the existing `staff_note = COALESCE(...)` pattern for the clarification reply.

Three scope calls confirmed with the user before implementation:

(1) **A stale active quote blocks booking; the Booking page never regenerates a quote itself.** The Quote page (Build 6) auto-persists only v1 and otherwise requires an explicit Regenerate click, and Streamlit's sidebar lets a customer reach Booking without revisiting Quote at all — so a customer can submit against an active quote that no longer matches their current inventory. Considered and rejected: silently regenerating on the Booking page (would split quote-version ownership across two pages) and warning-but-allowing-submit (the stored booking would then cite a price the customer never actually saw, since a stale Quote page displays the *freshly computed* numbers while `db.get_active_quote()` still returns the old row). Landed on: `booking_sync.booking_blockers()` compares the stored active quote against a freshly computed one via the same `quote_sync.quote_matches()` Build 6 already uses, and when it fails, the Booking page shows why and links back to Quote instead of offering a submit button — quote versioning stays owned by `quote_sync` alone.

(2) **`job.status` becomes `'booked'` only on staff confirmation, never on customer submit.** `booking_sync.submit_booking()` leaves the job at `'quoted'` and only creates the `pending_staff_review` booking row; `booking_sync.apply_staff_decision()` is the single place a booking status maps onto job status (module constant `STAFF_JOB_STATUS`: `confirmed → booked`, `cancelled → cancelled`; a clarification request or return to pending review leaves the job untouched).
